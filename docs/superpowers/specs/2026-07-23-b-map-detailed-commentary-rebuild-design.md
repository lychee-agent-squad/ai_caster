# B 地图详细解说重构设计

## 目标与范围

重构 `00_0721_回放/解说稿` 下 43241–43268 共 28 局 B 地图 2 倍速解说。只压缩开场动画和结算口播，游戏对战过程不得因固定分段或模板概括而丢失分路、任务、资源、鲜度、窗口争夺、设卡突破、小分队、宫宴冲刺、宫门验核和交付细节。

交付范围包括每局 `_2x_ui_synced.md`、机械派生的 `_2x_voice_only.md`、对应审计文件、批量验收报告，以及负责生成这些产物的 `tools/generate_b_map_commentary_batch.py`。不修改 `replay.txt`、`data.csv`、500ms 截图、捕获清单、B 地图源配置和 C 地图文件。

## 已确认根因

现有生成器用固定时间块选择少数代表事件，普通场次被压成 21–22 段。该结构会产生以下系统性问题：

- 15 秒开场同时承担动画、队名、对战面板、岭南果园和首个可玩状态。
- 首次路线选择未被当作独立关键事件，分路或共同选路缺少明确说明。
- 多步窗口、设卡、削弱、休整、重新移动被概括成一个结果句。
- 固定块边界可能把游戏过程最后动作和结算看板揉在一起。
- 稳定等待被模板化重复，而高价值对抗链反而被合并。
- 正式术语应为“宫门验核”，现稿多处使用“核验”。
- 路线判断未强制读取 B 地图的实际边长、路线类型、沿线任务、资源和固定处理。

因此不能只补写旧稿；必须修复生成逻辑并重建 28 局主稿。

## 开场设计

开场按实际画面拆成三个独立阶段。

1. 开场动画只报正式队名：`红队【正式队名】，对阵蓝队【正式队名】！`
2. 对战面板或岭南果园首个稳定画面出现后另起一段：`双方满载鲜荔，从岭南果园启程，过朱雀门、进兴庆宫！`
3. 首次实际移动、分路或共同选路另起一段。分别说明双方进入的路线边、路线类型和目标站点；两队同路时明确同路，不制造虚假分路。

开场动画口播约 3–5 秒。初始一百篓好果、鲜度一百保留在画面说明和回放锚点中，不再占用开场口播；只有后续数值对比需要时才重新播报。

## 路线解说设计

每次重要选路、分路或转线建立五项证据：实际进入路线、B 地图距离与类型、当前比赛行为、即时结果和后续印证。

路线判断使用 `可见选择 + 地图差异 + 有边界判断`。判断依据可以包括移动效率、鲜度损耗、沿线任务与资源、固定处理、障碍、天气和转线条件。意图未被后续事件证明时，只使用“看来”“可能”“更像”“这一步是在”等表达，不提前宣布完整路线计划。

## 对战过程保留规则

游戏过程不使用固定 16 秒网格。按事件触发、动作链和画面切换动态分段。不得删除任何改变路线、通行权、资源、鲜度、任务分、比分或交付状态的事件。

仅同一状态下没有新事件的连续移动或等待可以减少重复口播；状态发生变化的时刻、原因、代价和后续选择必须保留。

### 任务

说明处理队伍、完整任务名称、目标站点、窗口状态、完成/失败/过期/失去目标、任务基础分、任务分累计和里程碑。T04 任务清障必须与主车队或小分队普通清障区分。

### 资源与鲜度

资源按 `行动者 + 资源名称 + 实际效果 + 战术影响` 表达。探路标记只解释实际消费的那次处理。鲜度变化说明实际原因、首次跌破的阈值、好果转坏结果和双方差距，不能用泛称“果品折损”替代。

### 小分队

保留派出方、目标、行动类型、人手成本、落地结果和对主车队的影响。小分队削弱或清障不等于主车队已经移动或进入目标节点。

### 设卡与突破

完整跟踪设卡完成、生效、对手当时路线状态、对手实际回应、防守值变化、规则强制休整、设卡清除和后续真实进点。设卡清除不等于立即通过。

### 窗口争夺

高价值窗口保留争夺对象、三拍关键牌面、真实资源成本、胜负或平局、休整/冷却，以及限制结束后双方各自选择。禁止用“随后连续出现四次平局”替代不同窗口链。三拍不自动等于三篓好果，成本必须由出牌和资源变化证明。

### 同帧动作与等待

同一结算帧的独立行动按同步关系表达，不由日志顺序虚构因果。等待区分主动等待、系统等待、固定处理、休整、强制通行、宫门验核和缺动作。只有队伍已恢复自由行动并持续提交 `WAIT` 时，才可解释为主动等待；未知动机不得写成“观察对手”。

## 终局与结算设计

宫宴冲刺开放、终局急策、宫门验核、进入兴庆宫和交付仍属于游戏过程。最后一次游戏行动和结算看板必须分段，不能提前宣布正式胜者。

正式术语统一为“宫门验核”。普通结算简化为双方最终比分和正式胜者；一方未交付时只补充交付状态。只有实际画面存在掉线或异常结果反转时，才按“比分—画面转场—反转来了—可见结果原因—正式胜者”的顺序展开。

结算口播通常控制在 8–12 秒，不默认朗读全部分项差额。

## 节奏与时间轴

段数由事件密度决定：完整普通局预计 30–40 段，高对抗局可超过 40 段，提前结束局自然减少。段数不是压缩对战过程的硬上限。

节目终点仍不超过 `05:30`；保留原始 2 倍速，不按比例转换旧时间码。普通段口播密度为每秒 4.2–4.8 个单位，短促对抗段最高 5.5，全稿平均不超过 4.8。每段记录递增的源画面范围、可见 UI、回放锚点和解说目的。

## 生成器与数据流

生成器改为先从回放构建关键事件链，再使用帧证据分配画面边界：

`replay + B 地图 + 任务书 -> 规则分类与事件链 -> 500ms UI 边界 -> UI 同步主稿 -> 机械派生纯口播 -> 审计`

生成逻辑必须：

- 识别开场动画、对战面板/岭南果园、首次路线和结算看板边界。
- 移除固定 16 秒切段。
- 保留任务、资源、鲜度、天气、窗口、设卡、突破、小分队、宫宴冲刺、验核和交付链。
- 按 B 地图实际路线数据生成路线比较。
- 禁止无证据的动机模板。
- 统一“宫门验核”。
- 从 UI 主稿机械派生纯口播。

## 自动与人工验收

自动审计验证：

- 开场动画、对战面板/岭南果园、首次行动分别成段。
- 最后游戏行动和结算看板分别成段。
- 关键事件覆盖、正式术语、正式队名、比分、交付状态和胜者正确。
- UI 主稿与纯口播逐字一致，纯口播无时间码、帧号、路径或制作说明。
- 时间轴连续且不超过 `05:30`，单段和全稿语速通过。
- 备份哈希通过，源回放与帧证据未修改。

人工复核验证：

- 每次重要选路均有地图依据和正确的知识边界。
- 每次直接对抗同时说明双方行动与后续退出状态。
- 窗口平局后说明休整、冷却和双方下一选择。
- 设卡清除、强通完成与真实进点不混淆。
- 小分队不被描述成主车移动。
- 全稿相邻段落推进比赛，不重复同一结论。
- 28 局全部通过才能宣称完成。
