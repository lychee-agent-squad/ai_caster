# C 地图 330 秒解说稿刷新设计

## 目标

将 `00_0720_回放/解说稿` 下 42177–42204 共 28 局 C 地图解说重构为可剪辑的 2 倍速节目稿。每局节目时间轴不得超过 `05:30`，其中开场与最终结算合计约 30 秒，按原始 2 倍速播放的比赛内容约 5 分钟。B 地图 43241 的 `_2x_ui_synced.md` 是结构和节奏标杆，对应 C 地图的 `_2x_tts_ui_synced.md`。

## 权威输入

- C 地图源场次：`00_0720_回放/C地图对战结果/output_c_071805/LitchiDelivery_C/<match_id>/server/`
- 每局事实源：`replay.txt`、`data.csv`、现有回放时间线、证据文件和已确认的 2 倍速截图。
- 当前正式队名：`00_0720_回放/team_roster.md`。
- 当前解说规范：`lychee-replay-esports-commentator` Skill。
- B 地图节奏标杆：`00_0721_回放/解说稿/43241/43241_2x_ui_synced.md`。

实际 2 倍速 UI 决定画面顺序和剪辑锚点，`replay.txt` 决定事件、数值、比分与赛果。重构不得修改源回放事实，也不得通过改变源播放速度满足时长上限。

## 节目时间轴设计

每局保留完整的原始 2 倍速捕获作为证据，另行构建不超过 330 秒的节目时间轴：

1. 开场只保留建立正式队名、初始资源和目标所需的画面。
2. 比赛主体按时间顺序选取影响路线、资源、鲜度、任务分、对抗、核验、送达和赛果的片段。
3. 删除无事件移动、重复等待、重复规则说明和不改变局势的状态保持画面。
4. 同一短时间窗口内的连续动作合并为一个可读节拍。
5. 最终结算保留比分、结果反转（如有）和正式胜者宣布；胜者必须最后落点。
6. 每个节目段记录原始 2 倍速源画面范围或可追溯截图锚点，源范围必须保持时间递增。

目标通常为 20–24 段、1100–1450 个口播单位。它们是节奏目标，不得为了凑段数删除赛果关键事件。全稿平均密度不得超过 4.8 个口播单位/秒，单段不得超过 5.5 个口播单位/秒。

## 正式交付文件

每个场次活动目录最终保留以下正式内容：

- `<match_id>_2x_tts_ui_synced.md`：唯一的 UI 对应主稿。
- `<match_id>_2x_tts_voice_only.md`：从主稿机械提取的纯口播版。
- `<match_id>_2x_tts_audit.json`：针对 330 秒交付规则的新审计结果。
- `<match_id>_2x_tts_export_checks.json`：只验证 UI/口播一致性和口播清洁度，不再要求 SSML 或导演稿。
- `replay.txt`：从该场次 `server/replay.txt` 原样复制。
- `data.csv`：从该场次 `server/data.csv` 原样复制。
- 原有时间线、证据、捕获清单、截图和回放分析文件。

复制后的 `replay.txt`、`data.csv` 必须与源文件 SHA-256 一致。它们是只读交付输入，不得在解说刷新过程中改写。

## 移除范围

修改前先备份并校验，之后从活动场次目录移除：

- 42177–42182 的 `<match_id>_2x_ui_synced.md`。
- 42177–42182 的 `<match_id>_2x_voice_only.md`。
- 42177–42182 的 `<match_id>_2x_audit.json`，因为它只对应被移除的旧版正文。
- 28 局全部 `<match_id>_2x_tts_ssml.xml`。
- 28 局全部 `<match_id>_2x_tts_director.md`。

不创建新的 SSML 或导演稿。B 地图现有文件和通用导出能力不在本次删除范围内。

## 备份与可恢复性

在 `00_0720_回放/解说稿/backups/2x_330s_20260722_before_edit/` 下按场次保存所有将被改写或移除的活动文件。根目录生成包含原路径、备份路径、文件大小和 SHA-256 的清单。只有在原件与备份哈希一致后，才允许改写或移除活动文件。

备份目录不参与活动稿审计，也不参与“旧版文件应为零”的最终扫描。

## 工具兼容设计

现有 `tools/generate_lychee_tts_exports.py` 仍需兼容 B 地图的 SSML、导演稿导出。为 C 地图增加只生成纯口播和检查报告的模式，不破坏原参数行为。

`tools/audit_lychee_tts_batch.py` 调整为 C 地图 330 秒交付配置：

- 显式传入 `--max-timeline-seconds 330`。
- 启用 `--max-average-rate 4.8`、`--max-rate 5.5` 和 `--require-live-style`。
- 段数范围适配剪辑稿，不再沿用 28–38 段旧范围。
- 批量结果只接受口播派生检查，不再要求已移除的 SSML 和导演稿。
- 汇总每局时间轴终点、口播单位、平均密度、最大密度和失败原因。

## 内容重构方法

以现有 `_2x_tts_ui_synced.md` 为事实完整稿，逐局完成以下过程：

1. 读取现有段落、回放锚点、时间线、证据和源 `replay.txt`。
2. 将段落分为开场、关键动作、结果/后果、低价值移动等待、结算五类。
3. 优先删除低价值移动等待，合并相邻的因果链与重复分析。
4. 为保留段落建立新的连续节目时间码，并记录原始 2 倍速源画面锚点。
5. 在不改变事实的前提下缩短台词，保持双方动作、立即结果和战术后果可听懂。
6. 从完成的主稿机械生成纯口播版，禁止独立改写纯口播版。

平局、结果反转、长等待、掉线和异常结算必须按各自真实事件保留，不能套用统一模板。

## 验收标准

批量交付必须同时满足：

- 28 局主稿均从 `00:00` 连续开始，终点不超过 `05:30`。
- 开场和结算完整，比赛主体保留所有赛果关键动作。
- 所有节目段均能追溯到时间递增的原始 2 倍速源画面。
- UI 主稿与纯口播逐段、逐字一致。
- 全稿平均密度不超过 4.8，单段密度不超过 5.5。
- 正式队名、比分、胜者和平局状态与源回放一致。
- 现场口语风格、至少三类事件情绪和粒子滥用检查通过。
- 28 局活动目录均存在且仅存在对应的 `replay.txt`、`data.csv`，并与源文件哈希一致。
- 活动目录中旧版 `_2x_ui_synced.md`、旧版 `_2x_voice_only.md`、旧版 `_2x_audit.json`、全部 SSML 和全部导演稿为零。
- 备份清单全部通过 SHA-256 校验。
- C 地图批量审计结果为 28/28 通过。

## 非目标

- 不修改 B 地图 43241 或其他 B 地图交付物。
- 不修改源 `replay.txt`、`data.csv`、截图、捕获清单或比赛事实。
- 不重新命名 C 地图当前 `_2x_tts_*` 正式文件系列。
- 不通过提升源视频播放速度或简单按比例缩放旧时间码来满足 330 秒上限。
