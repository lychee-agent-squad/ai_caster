# 荔枝回放解说 Skill：TTS 交付与口语校对设计

## 目标

当用户需要用 AI 生成游戏解说音频时，`lychee-replay-esports-commentator` 除了产出事实准确、与 UI 同步的解说稿，还要提供能直接交给常见语音工具使用的 TTS 衍生稿。所有衍生稿必须来自同一份口播文本，不能各自改写。

普通解说任务仍默认交付 UI 同步稿和纯配音稿。只有用户提出 TTS、AI 配音、SSML、语调、语速或导演提示时，才启用 TTS 交付分支。

## 文件结构

本次更新采用“主流程入口 + 专项引用”的结构：

- `SKILL.md`：识别 TTS 需求，加载专项引用，并在工作流和完成标准中加入 TTS 条件分支。
- `references/tts-delivery.md`：定义通用 SSML、自然语言导演提示、情绪曲线、语速和停顿规则。
- `references/output-contract.md`：定义普通文件与 TTS 文件的命名、用途和文本一致性要求。
- `references/commentary-style.md`：增加口播语法与朗读检查。
- `tests/test_skill_contract.py`：用契约测试防止后续修改遗漏这些规则。

不拆分新的 TTS Skill。TTS 稿依赖已经核实的回放事实、UI 时间轴和口播文本，留在同一个 Skill 中可以避免事实与配音稿脱节。

## 交付契约

### 普通交付

未提出 TTS 需求时，沿用原文件名：

| 文件 | 用途 |
|---|---|
| `<project>_<speed>_ui_synced.md` | UI 画面、回放锚点、时间段和解说词的主稿 |
| `<project>_<speed>_voice_only.md` | 仅含口播文字的纯配音稿 |
| `<project>_<speed>_audit.json` | 普通稿审计结果；仅在需要机器报告时生成 |

### TTS 交付

提出 TTS 需求时，保留原稿，并生成以下衍生文件：

| 文件 | 用途 |
|---|---|
| `<project>_<speed>_tts_ui_synced.md` | 完成口语优化后的 UI 同步主稿 |
| `<project>_<speed>_tts_voice_only.md` | 从 TTS UI 主稿机械提取的纯口播稿 |
| `<project>_<speed>_tts_ssml.xml` | 使用通用 SSML 1.1 标签的语音合成稿 |
| `<project>_<speed>_tts_director.md` | 逐段自然语言导演提示和对应原文 |
| `<project>_<speed>_tts_audit.json` | TTS 衍生稿的一致性和格式审计结果 |

文件名中的 `tts` 表示“为语音合成优化后的衍生版本”，不是另一个比赛版本。没有 `tts` 的文件是原始基线稿，默认保留，不能被 TTS 优化覆盖。

## 单一文本源

TTS UI 同步稿是 TTS 分支的唯一文字主稿。其余三个可朗读文件按以下顺序生成：

1. 从 TTS UI 同步稿提取每段 `**解说：**`，生成 TTS 纯配音稿。
2. 在完全相同的口播文字外添加 SSML 标签，生成 SSML 稿。
3. 给每段完全相同的口播文字添加导演提示，生成导演稿。

去掉 SSML 标签和导演提示后，三份衍生稿的口播文字必须与 TTS 纯配音稿逐段一致。SSML 和导演提示只能控制读法，不能新增事实、口号、解释或语气词。

## 通用 SSML

默认使用兼容性较高的 SSML 1.1 子集：`speak`、`p`、`s`、`prosody`、`break`、`emphasis`。不默认使用厂商专属标签。

每个 UI 时间段对应一个 `p` 段。标签负责表达局部语速、音高、音量、停顿和重点，不能把整篇稿件固定为同一种高亢状态。语速变化遵循比赛节奏：

- 移动和分析段保持自然、清楚；
- 冲突开始时适度加快；
- 结果句短促落地；
- 规则、密集数字和结算段适当放慢；
- 比分、反转和胜者前后留出可听见的停顿。

如目标工具不支持某个通用标签，只降级标签，不改口播文字。

## 自然语言导演提示

导演稿按 UI 时间段逐段生成。每段包含：

1. 时间范围；
2. 当前播报任务；
3. 情绪和强度；
4. 语速与节奏；
5. 重音与停顿；
6. 禁止读法；
7. 与 TTS 纯配音稿一致的原文。

提示必须具体说明“这一段怎么读”，不能只写“激动一点”或“像职业解说”。导演提示不进入实际口播文本。

整场情绪应有起伏：铺垫、触发、动作链、结果、解释、重置。不要让每段都保持满强度，也不要依靠连续感叹号制造赛事感。

## 口播语法与去 AI 味检查

完成事实校验后，对整份 TTS 口播稿逐句朗读检查。每个关键句应让听众一次听清以下内容：

- 谁在行动；
- 做了什么；
- 动作指向哪里或什么对象；
- 产生了什么结果。

实时短句可以省略不影响理解的成分，但不能把地点、判断和动作并列成缺少谓语关系的碎片。涉及两队时，切换行动主体必须重新说出队名或颜色。

示例：

- 不推荐：`关口位置，看样子红队要先抢。`
- 推荐：`看样子，红队想抢先占住潼关。`

推荐句明确了主语“红队”、动作“抢先占住”和对象“潼关”，也保留了现场判断的不确定性。

逐句检查还要清除以下问题：

- 只有名词堆叠，没有明确动作；
- 主语在红蓝两队之间跳转，却使用“它”“对方”或省略主语；
- `但`、`却`、`反而`没有真实转折；
- 为了显得激动而增加空洞口号、套话或连续感叹；
- 书面规则句过长，正常朗读时一口气说不完；
- 同一事实分别在 UI 稿、纯配音稿、SSML 稿和导演稿中被改成不同说法。

## 验证

契约测试至少确认：

- 主 Skill 能识别 TTS、SSML、AI 配音和导演提示需求；
- TTS 专项引用存在，并由主 Skill 明确要求读取；
- 普通文件与 TTS 文件命名均有定义；
- SSML 只使用通用标签子集；
- 导演提示按段对应原文；
- 四类 TTS 稿遵守单一文本源和逐段一致性要求；
- 口播语法检查包含主语、动作、对象、结果；
- 已知病句和推荐改法被写入规则。

运行现有全部测试和 Skill 结构验证。更新不能破坏原有回放事实、UI 同步、队名、倍速和结算规则。

## 完成标准

更新完成后，默认行为如下：

- 任务未涉及 TTS：继续交付普通 UI 同步稿和纯配音稿。
- 任务涉及 TTS：在保留普通基线稿的前提下，生成带 `tts` 的 UI 同步稿、纯配音稿、SSML 稿、导演稿和审计报告。
- 用户明确要求不同格式或交付范围：按用户要求执行，但仍保持事实正确和可朗读文本一致。
